---

## 1. Why Classical Baselines Are Necessary

SIH26139 asks for quantum-enhanced models to be compared against classical baselines. That comparison is only meaningful if the classical side is a **genuine, fairly-tuned effort** — not a weak strawman a quantum model can trivially beat.

**This phase's purpose is explicitly not to show classical ML is bad.** It is to answer, as rigorously as a 303-record dataset allows: *how good can a well-tuned classical model actually get on this problem, under leakage-safe conditions, with honestly reported uncertainty?* Whatever a future QSVM or VQC achieves will be measured against these exact numbers, on the exact same locked test split, using the exact same preprocessing pipeline (Phase 2, reused without modification).

If the classical benchmark were weak, sloppy, or leaky, any later "the quantum model is competitive" claim would be worthless. Phase 3 is the control arm of the experiment, and a control arm has to be trustworthy.

---

## 2. Why Accuracy Alone Is Insufficient

This is a **medical early-risk detection problem**. The two ways a model can be wrong have very different real-world consequences:

- **False negative** (model says "no risk," patient actually has disease): the patient loses the early-intervention window this whole project is motivated by.
- **False positive** (model says "at risk," patient does not have disease): the cost is a follow-up test.

A model can post a high accuracy while being clinically poor — e.g., a model that always predicts "no disease" on this near-balanced (54.1%/45.9%) dataset would still be right 54% of the time, while catching **zero** at-risk patients (0% sensitivity). Accuracy does not distinguish this failure mode from a genuinely useful model. That is why this phase's model-selection criterion (Section 12) is **not** accuracy, and why sensitivity and specificity are reported as first-class metrics, not afterthoughts.

**Sensitivity** (= Recall): the fraction of patients *with* disease/risk that the model correctly identifies. `TP / (TP + FN)`.
**Specificity**: the fraction of patients *without* disease/risk that the model correctly identifies. `TN / (TN + FP)`.

Neither is "the good one" — a model that only maximizes sensitivity (e.g., by predicting "at risk" for everyone) is useless too. Both are reported together, always.

## 3. Train/Test Strategy (reused from Phase 2, not rebuilt)

The 80/20 stratified split (242 train / 61 test, seed 42) is produced by `src.preprocessing.pipeline.run_preprocessing_pipeline()` / `split_dataset()` from Phase 2 — **unchanged**. Phase 3 does not re-split the data, does not use a different seed, and does not touch `data/raw/`.

**The critical rule, restated for this phase specifically:** the 61-record test split is used **exactly once per model, per experiment** — after every hyperparameter tuning decision has already been made using the training split alone. See Section 13.

## 5. Leakage Prevention — the Core Engineering of This Phase

### 5.1 The rule

> Fold training data → fit preprocessing (impute, encode, scale, select, PCA) → train model.
> Fold validation data → **transform only** using that fold's fitted preprocessing → predict.

Fitting the Phase 2 pipeline once on the whole training set and *then* cross-validating on top of its already-fitted output would leak fold-validation rows' influence (via the imputer's median, the scaler's mean, the selector's ranking, the PCA axes) into every fold — even though the *label* is never seen, the *feature statistics* would be. This phase avoids that entirely.

### 5.2 How it is implemented — reusing Phase 2, not rewriting it

Phase 2's `SharedFeaturePipeline` and `build_quantum_pipeline` already do exactly the right thing (fit on train, transform on test) — but they are plain Python classes, not sklearn estimators, so they cannot be dropped directly into `GridSearchCV`. Two thin **adapters** in `src/classical/tuning.py` — `SharedFeatureTransformer` and `QuantumReadyTransformer` — wrap them to satisfy sklearn's `clone()`/`get_params()` contract. **Neither adapter reimplements any preprocessing logic**; both delegate every `.fit()`/`.transform()` call straight to the Phase 2 objects.

```python
Pipeline([
    ("shared", SharedFeatureTransformer(feature_groups, config)),   # impute+encode+scale+select
    # ("quantum", QuantumReadyTransformer(...)),                    # only for the PCA/quantum-ready experiment
    ("model", classifier),
])
```

This whole pipeline — preprocessing included — is what gets handed to `GridSearchCV`. **`GridSearchCV`'s own, independently-tested cross-validation machinery** then does the leakage-safe work: for every fold and every hyperparameter combination, it clones the pipeline fresh and calls `.fit()` on the fold's training rows only (which re-fits the imputer, scaler, encoder, selector, and PCA strictly within that fold), then scores on the fold's held-out rows via `.transform()` only.

**This was proven, not assumed** — `tests/test_classical.py::test_preprocessing_refits_independently_per_cv_fold` fits the shared preprocessing on two different partitions of the training data and confirms the learned imputer statistics differ; `test_quantum_ready_pca_refits_independently_per_fold` does the same for PCA components.

### 5.3 What "final test set untouched during tuning" means concretely

| Guarantee | How it is enforced | How it is tested |
|---|---|---|
| `run_grid_search()` cannot use the test set | Its function signature has **no test-set parameter at all** — there is no `X_test`/`y_test` argument for it to accidentally reference | `test_run_grid_search_has_no_test_set_parameter` inspects the function's signature directly |
| Tuning decisions are identical regardless of what the test set contains | Two identical grid searches, one run alongside a wildly perturbed (but unused) copy of the test set, produce identical CV scores and identical best hyperparameters | `test_cv_scores_unaffected_by_test_set_perturbation` |
| The test set is scored exactly once, after tuning | `evaluate_on_test()` is a **separate function**, called only after `run_grid_search()` returns a fitted `best_estimator_` | `test_evaluate_on_test_is_the_only_place_test_labels_are_scored`, and the architecture of `train_baselines.py::run_experiment()` itself (tuning and evaluation are two distinct, sequential steps) |
| No threshold, feature, or model choice is optimized against the test set | The 0.5 threshold is fixed in advance (Section 11); feature selection and PCA are fit inside CV folds (Section 5.2); model selection uses CV ROC-AUC only (Section 12) | Architectural — the test set literally never appears in any of these decisions' code paths |

## 6. Hyperparameter Tuning

**Method:** `GridSearchCV`, one small, documented grid per model — not an enormous search, appropriate for 242 training rows. Every grid and its rationale is defined in `src/classical/models.py` and reproduced below.

| Model | Parameters tuned | Grid | Rationale (abbreviated — full text in `models.py`) |
|---|---|---|---|
| **Logistic Regression** | `C` | `{0.001, 0.01, 0.1, 1, 10, 100}` | Spans strong to weak L2 regularization on standardized features. *(An l1-vs-l2 comparison was considered but dropped — see the note in Section 7.)* |
| **RBF-Kernel SVM** | `C`, `gamma` | `C ∈ {0.1, 1, 10, 100}`, `gamma ∈ {scale, 0.01, 0.1, 1}` | `gamma='scale'` (data-driven default) plus a 3-order-of-magnitude manual sweep, appropriate for standardized, low-dimensional (10–17 feature) input. |
| **Random Forest** | `n_estimators`, `max_depth`, `min_samples_split`, `max_features` | `{100,300} × {3,5,None} × {2,5} × {sqrt,log2}` (24 combos) | Depth and split thresholds bracket regularized-to-unrestricted trees, appropriate for only ~242 rows where deep unrestricted trees risk overfitting. |
| **XGBoost** | `n_estimators`, `max_depth`, `learning_rate`, `subsample`, `colsample_bytree` | `{100,300} × {2,3,4} × {0.05,0.1} × {0.8,1.0} × {0.8,1.0}` (48 combos) | Shallow trees (depth 2–4) and row/column subsampling as explicit regularizers against overfitting a small dataset. |

Model selection within each grid search uses **mean CV ROC-AUC** as the refit criterion (Section 12) — not accuracy, per Section 2.

## 7. Each Model

| Model | Library | Why included |
|---|---|---|
| **Logistic Regression** | `sklearn.linear_model.LogisticRegression` | Interpretable linear baseline; coefficients map directly to clinical features (Section 15). The clinical-research standard against which nearly all of the published UCI Heart Disease literature is compared. |
| **RBF-Kernel SVM** | `sklearn.svm.SVC(kernel='rbf', probability=True)` | The **direct classical counterpart to a future QSVM** — a support vector machine differs from QSVM only in the kernel (classical RBF vs. a quantum fidelity kernel). Any measured difference later will be attributable to the kernel and (almost) nothing else. |
| **Random Forest** | `sklearn.ensemble.RandomForestClassifier` | A non-linear, non-parametric baseline; captures feature interactions a linear model cannot. |
| **XGBoost** | `xgboost.XGBClassifier` | A strong, widely-used gradient-boosted baseline; the realistic performance ceiling for tabular data at this scale. **Available in this environment** (`xgboost==3.2.0`) — see Section 7.1 for the fallback policy if it were not. |

### 7.1 XGBoost availability

`src/classical/models.py` attempts `import xgboost` and records the outcome in `XGBOOST_AVAILABLE` / `XGBOOST_IMPORT_ERROR`. **In this environment, XGBoost imported successfully (`xgboost==3.2.0`) and all four models ran.** Per the phase instructions, if it had been unavailable, XGBoost would have been **omitted with the reason logged and printed** (`run_experiment` prints a `WARNING` line, and `run_record.json` records `xgboost_available: false` with the exact import error) — never silently swapped for a different model.

### 7.2 A note on the Logistic Regression grid (an sklearn version issue, not a design choice)

The originally planned grid also swept `penalty ∈ {l1, l2}`. During development, the installed `scikit-learn==1.8.0` was found to have deprecated the `penalty` keyword in favor of a unified `l1_ratio` API, and combining `penalty='l1'` with `solver='liblinear'` under that transition emitted `"Inconsistent values: penalty=l1 with l1_ratio=0.0"` — a warning suggesting the l1 request might not be honored as expected in this sklearn version. Rather than depend on ambiguous, version-specific behavior, Logistic Regression tunes only `C` with the standard L2 penalty via the `lbfgs` solver (sklearn's current default, with no such edge case). This is documented, not silently patched over — see the code comment in `models.py`.

## 8. Metrics

Computed on the locked test set at the default 0.5 probability threshold (label metrics) and directly from predicted probabilities (ROC-AUC, PR-AUC — threshold-independent):

| Metric | Formula | What it answers |
|---|---|---|
| Accuracy | `(TP+TN)/N` | Overall correctness — reported, but never used to select a model (Section 2) |
| Precision | `TP/(TP+FP)` | Of predicted-at-risk patients, how many actually are |
| **Sensitivity (Recall)** | `TP/(TP+FN)` | Of actually-at-risk patients, how many the model catches |
| **Specificity** | `TN/(TN+FP)` | Of actually-healthy patients, how many the model correctly clears |
| F1 | Harmonic mean of precision & sensitivity | A single balanced number, still not a substitute for reporting sensitivity/specificity separately |
| **ROC-AUC** | Area under the ROC curve | Ranking quality across *every* possible threshold — the model-selection criterion (Section 12) |
| **PR-AUC** | Area under the precision–recall curve | More informative than ROC-AUC would be under class imbalance (this dataset is close to balanced, but PR-AUC is reported regardless for consistency with later, possibly more imbalanced, experiments) |
| Confusion Matrix | TN, FP, FN, TP | The raw counts everything above is computed from |

## 9. Model-Selection Methodology

**The selection criterion is mean cross-validation ROC-AUC** (`src.classical.tuning.MODEL_SELECTION_METRIC = "roc_auc"`), computed on the training split only, via `GridSearchCV(..., refit="roc_auc")`.

**Why ROC-AUC and not accuracy:** ROC-AUC is threshold-independent — it measures how well a model *ranks* at-risk patients above healthy ones across the full range of possible decision thresholds, without committing to one clinical operating point in advance (Section 11 explains why 0.5 is not assumed to be the medically optimal threshold). Per the phase instructions, **accuracy alone is explicitly rejected** as a selection criterion (Section 2).

**Why CV, not the single test-set score:** with only 242 training rows and 61 test rows, a single score is noisy. Cross-validation averages over 5 different train/validation partitions, giving a materially more trustworthy estimate of how a hyperparameter combination will generalize than any one split can. **The CV number, not the test-set number, is the primary evidence used during model selection** — the test-set score is reserved entirely for the final, one-time confirmation (Section 13).

---

## 10. Confidence and Variability — Two Kinds, Kept Separate

| Kind | Source | Method | Used for |
|---|---|---|---|
| **CV variability** | 5 fold scores from the training split, at the best hyperparameters | Mean, std, and a t-distribution confidence interval (`scipy.stats.t`, appropriate for a small number of fold scores rather than assuming normality or bootstrapping too few numbers) | Understanding how stable a model's performance is *before* it ever sees the test set |
| **Final test CI** | The single, locked evaluation on 61 test records | Percentile bootstrap (1000 resamples of the 61 test predictions) | Quantifying the uncertainty around the one number that matters for the final comparison |

These two are **never conflated** in the code, the results files, or this document. A model's CV mean and its test-set score can and do differ (see Section 13) — that is expected, not an error.

---

## 11. Threshold Handling

The headline metrics use the default **0.5 probability threshold**. This is **not** claimed to be the medically optimal operating point — no threshold was chosen by inspecting the test set, and no threshold-selection step of any kind touches the test set anywhere in this phase. `ROC-AUC` and `PR-AUC` are reported specifically because they are threshold-independent and therefore preserve full information for a **later** threshold analysis (e.g., choosing a sensitivity-targeted threshold on training-fold data only), which is out of scope for Phase 3.

## 12. Class Imbalance — Evaluated, Not Assumed

The binary target is **164 no-disease / 139 at-risk (54.1% / 45.9%)** — close to balanced. Per the phase instructions, **no SMOTE or oversampling was applied**, and class weighting was **tested explicitly rather than assumed necessary or unnecessary**.

**Method:** for each of Experiment 1's already-tuned models, a fresh 5-fold CV comparison (same seed, same fixed hyperparameters) was run with `class_weight='balanced'` (or, for XGBoost, `scale_pos_weight = n_negative/n_positive`) against the unweighted baseline.

**Actual result (`results/classical/class_weighting_comparison.json`):**

| Model | Unweighted CV ROC-AUC | Weighted CV ROC-AUC | Unweighted Sensitivity | Weighted Sensitivity | Unweighted Specificity | Weighted Specificity |
|---|---|---|---|---|---|---|
| Logistic Regression | 0.9019 | 0.9012 | 0.7470 | 0.7648 | 0.8923 | 0.8769 |
| RBF-Kernel SVM | 0.9055 | 0.9035 | 0.7470 | 0.7648 | 0.9308 | 0.8846 |
| Random Forest | 0.8894 | 0.8908 | 0.7289 | 0.7735 | 0.9003 | 0.8618 |
| XGBoost | 0.8871 | 0.8874 | 0.7375 | 0.7557 | 0.8387 | 0.8234 |

**Conclusion:** class weighting makes **no meaningful difference to ROC-AUC** (all four changes are within ±0.002, well inside CV noise) and produces the expected, small sensitivity-up/specificity-down trade-off (weighting toward the positive class predictably raises sensitivity slightly at the cost of specificity). This is exactly the expected result on a near-balanced dataset, and it was **confirmed empirically rather than assumed** — the phase instructions' concern was legitimate to check, and checking it cost four fast CV re-fits. **Given no meaningful benefit, class weighting is not used in the primary (unweighted) results reported elsewhere in this document.**

## 14. `ca` / `thal` Ablation — Experiment 1 vs. Experiment 2

**Motivation (from Phase 1):** `ca` (fluoroscopy vessel count) and `thal` (thallium stress test result) are results of specialist cardiac investigations typically ordered once disease is already suspected. A model that leans heavily on them may overstate what is achievable in a genuine *early*-detection setting, where such specialist results may not yet be available.

**Cross-validation ROC-AUC, side by side:**

| Model | Experiment 1 (full, 13 features) | Experiment 2 (screening, 11 features — no ca/thal) | Drop |
|---|---|---|---|
| Logistic Regression | 0.9019 | 0.8540 | −0.0479 |
| RBF-Kernel SVM | 0.9055 | 0.8487 | −0.0568 |
| Random Forest | 0.8894 | 0.8386 | −0.0508 |
| XGBoost | 0.8871 | 0.8370 | −0.0501 |
| **Mean across all 4 models** | **0.8960** | **0.8446** | **−0.0514** |

**Every single model's CV ROC-AUC dropped when `ca` and `thal` were removed — consistently, by roughly 5 percentage points, with no exceptions.** This is not noise from one unlucky model; it is a uniform effect across four architecturally different classifiers, which is strong evidence that `ca`/`thal` genuinely carry substantial predictive signal beyond what the other 11 features provide.

**Interpretation:** this confirms the Phase 1 concern was well-founded. A ~5-point ROC-AUC drop is a real, measurable cost of restricting to features plausibly available at an *early* screening stage, before specialist cardiac investigation. **Neither number is "more correct" than the other** — Experiment 1 is the literature-comparable, maximum-information benchmark; Experiment 2 is the more clinically honest estimate of what a genuinely early-detection model can achieve. Both are reported, side by side, exactly as the phase instructions require, and **`ca`/`thal` were never removed from the primary dataset or pipeline** — Experiment 2 is a config change (`feature_set="screening"`), not a data modification.

Full CV and test tables for Experiment 2 are in `results/classical/experiment2_screening_classical/`.

## 15. Experiment 3 — The Quantum-Ready (PCA-Reduced) Benchmark

**Why this experiment exists:** a future QSVM/VQC model will not see the 10-feature classical-ready representation — it will see the **4-dimensional, PCA-reduced, `[0, π]`-normalized** quantum-ready representation from Phase 2 (§8), because near-term quantum hardware supports only a handful of qubits. Comparing a future quantum model against Experiment 1's classical numbers would be comparing it against classical models that got to see *more* information — an unfair advantage for the classical side. Experiment 3 answers the fair question: **how good can a classical model get on the exact same compressed representation the quantum branch will use?**

**Cross-validation ROC-AUC, full feature set, PCA-reduced (4 components) vs. classical-ready (10 features):**

| Model | Experiment 1 (classical-ready, 10 features) | Experiment 3 (quantum-ready, 4 PCA components) | Drop |
|---|---|---|---|
| Logistic Regression | 0.9019 | 0.8610 | −0.0409 |
| RBF-Kernel SVM | 0.9055 | 0.8604 | −0.0451 |
| Random Forest | 0.8894 | 0.8486 | −0.0408 |
| XGBoost | 0.8871 | 0.8616 | −0.0255 |
| **Mean across all 4 models** | **0.8960** | **0.8579** | **−0.0381** |

Compressing to 4 PCA components (which retain 82.0% of the variance present in the 10 selected features — see `docs/PREPROCESSING.md` §8) costs roughly **3.8 ROC-AUC points on average** — a real, measurable, and expected consequence of dimensionality reduction, reported here rather than hidden. **This is now the concrete number a later QSVM/VQC model must be compared against on equal footing** (same 4-dimensional input, same split, same evaluation methodology): CV ROC-AUC ranging from 0.849 (Random Forest) to 0.862 (XGBoost) across the four classical models.

Full CV and test tables for Experiment 3 are in `results/classical/experiment3_full_quantum_ready/`.

## 17. Limitations of the 303-Sample Dataset

| # | Limitation | Consequence for Phase 3 results |
|---|---|---|
| 1 | Only 242 training / 61 test records | CV fold scores have real spread (std up to ±0.09 on some metrics); the 61-record test set gives wide bootstrap CIs (e.g., ROC-AUC CIs spanning ~0.11 wide). No single point estimate in this document should be read as precise to more than roughly ±0.03–0.05. |
| 2 | Model ranking is not decisive | As shown in Section 13, the CV-best model (SVM) and the test-best model (Logistic Regression) disagree, and all four models' test ROC-AUC values overlap within their bootstrap CIs. **No model in this benchmark is confidently "the best"** — only "among the best, with SVM/LogReg CV-favored." |
| 3 | Grids are intentionally small | Per instruction, hyperparameter search was proportionate to dataset size, not exhaustive. A materially larger search was not attempted and might shift rankings slightly, though likely not outside the CV noise already observed. |
| 4 | Single-site, historical data | Same limitation as Phase 1/2 — Cleveland Clinic, 1988. These numbers describe performance on this cohort, not a modern or geographically diverse population. |
| 5 | Class-weighting conclusion is dataset-specific | The "no meaningful benefit" finding (Section 12) holds because this dataset is 54/46 balanced. It would not necessarily hold on a more imbalanced dataset (e.g., a real-world screening population where disease prevalence is much lower). |
| 6 | Calibration plot is exploratory only | With only 61 test records split across probability bins, the calibration plots (`results/classical/figures/*_calibration.png`) are illustrative, not a rigorous calibration assessment. |
| 7 | Rare categorical levels can vanish from a CV fold | `restecg` level 1 has only 4 records total; occasionally a 5-fold split leaves a fold-training partition with none of a rare level. `OneHotEncoder(handle_unknown='ignore')` (Phase 2 design) handles this correctly (encodes as all-zero) rather than crashing, but it is a real, observed consequence of small-fold CV on this dataset, not a hypothetical edge case. |

## 18. Why This Is the Benchmark for Later Quantum Models

Everything in this phase was built so that a future QSVM/VQC/QNN model can be compared against it **fairly**, not aspirationally:

- **Same split, same seed** — a future quantum model will be evaluated on the identical 61-record locked test set, from the identical `split_id` produced by Phase 2.
- **Same preprocessing** — the quantum branch will consume the exact Phase 2 `SharedFeaturePipeline` + PCA + range-normalize chain used here, not a parallel, potentially inconsistent pipeline.
- **A same-representation baseline already exists** — Experiment 3 is exactly the "classical model, same 4-dimensional input a quantum model will see" comparison (Protocol A, in the project's terminology), so a quantum result will not be silently compared against classical models that had access to more information.
- **A best-case classical baseline also exists** — Experiment 1 is the classical ceiling with full information, for the practical comparison (Protocol B).
- **Explicit uncertainty, not point estimates** — every classical number here carries a CV std and/or a bootstrap CI. A future quantum result will be expected to carry the same, and any comparison will use a paired significance test (McNemar / DeLong), not a bare delta — consistent with `PRD.md` §23 and `MVP_SPEC.md` §9.3.

**No claim is made here about whether a quantum model will beat, match, or lose to these numbers.** That is an empirical question for a later phase, not a conclusion of this one.
